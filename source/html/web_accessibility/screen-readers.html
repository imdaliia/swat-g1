Screen Readers

How software translates digital content into speech or Braille — and how developers can support it

By Andrii Synelnyk 6 min read

What is a Screen Reader?

A screen reader is a software application that interprets and renders the content of a screen in an alternative format — most commonly synthesized speech or a refreshable Braille display. Unlike optical character recognition (OCR), screen readers interact directly with a browser's accessibility API and the Document Object Model (DOM), traversing the semantic structure of a page rather than its visual layout.

Screen readers are indispensable for people who are blind or have severe visual impairments, but they also benefit users with dyslexia, cognitive differences, and situational disabilities (e.g. driving, bright sunlight). According to the WebAIM Screen Reader User Survey, over 70 % of screen reader users rely on them daily.

Popular Screen Readers

Several screen readers dominate the market across different platforms. Each has its own interaction model and keyboard shortcuts, so developers should test with more than one tool.

How Screen Readers Work

Screen readers expose an accessibility tree — a parallel representation of the DOM that strips presentational markup and exposes only the semantic roles, names, states, and properties of each element. This tree is built using platform-specific accessibility APIs:

  • Windows: UI Automation (UIA) and IAccessible2
  • macOS / iOS: NSAccessibility
  • Android: AccessibilityService API
  • Cross-platform: ATK/AT-SPI on Linux

When a user presses a key shortcut, the screen reader queries the accessibility tree for the focused element's role (e.g. button, link), name, and state (e.g. expanded, checked) and announces it via the speech engine.

Developer tip

Open your browser's built-in accessibility tree inspector (Chrome DevTools → Accessibility panel or Firefox → Accessibility tab) to see exactly what a screen reader will announce for each element.

Semantic HTML is the Foundation

The single most effective practice for screen reader support is using correct, native HTML elements. Native elements carry built-in roles, states, and keyboard behaviour that custom <div>-based widgets must laboriously replicate with ARIA.

Native elements vs. their ARIA equivalents
Native element Implicit role Avoid this ARIA workaround
<button> button <div role="button" tabindex="0">
<nav> navigation <div role="navigation">
<main> main <div role="main">
<input type="checkbox"> checkbox <div role="checkbox"> + JS

"The first rule of ARIA use is: if you can use a native HTML element or attribute with the semantics and behaviour you require already built in, instead of re-purposing an element and adding an ARIA role, state or property to make it accessible, then do so."

W3C WAI-ARIA Authoring Practices

Key Developer Practices

Meaningful alt text

Every informative image needs an alt attribute whose value conveys the purpose of the image in context. Decorative images should use alt="" so screen readers skip them.

Common mistake

Writing alt="image" or alt="photo.jpg" is worse than useless — it creates noise. Write what the image communicates, not what it looks like.

Landmark regions

Screen reader users navigate by jumping between landmark regions. Use <header>, <nav>, <main>, <footer>, and <aside>. When more than one of the same element appears on a page, distinguish them with aria-label.

Live regions for dynamic content

When content updates asynchronously (e.g. a toast notification, a live search result count), wrap it in an aria-live region so the screen reader announces the change without the user having to discover it manually. 

<div aria-live="polite" aria-atomic="true">
  <!-- dynamically injected update messages go here -->
</div>

Use aria-live="polite" for most updates. Reserve assertive for genuine errors that require immediate attention.

Descriptive link text

Screen reader users often browse a list of all links on a page. Links labelled "click here" or "read more" are meaningless out of context. Write links whose text describes the destination: "Read the WCAG 2.2 success criterion for focus appearance".

Heading hierarchy

Headings are the primary navigation mechanism for screen reader users. Use a single <h1> per page, then nest <h2> → <h3> logically. Never skip levels (e.g. jumping from h1 to h4) just for visual styling — adjust CSS instead.

Testing with a Screen Reader

You do not need to be a daily screen reader user to run basic accessibility tests. Here is a quick checklist for desktop testing with NVDA (Windows) or VoiceOver (macOS):

  • Turn on the screen reader and navigate the page using Tab alone — every interactive element should be reachable and announce its role and name.
  • Use the screen reader's heading-list command to verify the outline makes sense.
  • Use the screen reader's link-list command to check that every link is self-descriptive.
  • Fill out and submit a form using only the keyboard; listen to any error announcements.
  • Open an image and listen to its alt text.
Automated tools are a starting point, not an end point

Tools such as axe DevTools, Lighthouse, or WAVE catch about 30–40 % of accessibility issues automatically. Manual testing with a real screen reader is irreplaceable.
