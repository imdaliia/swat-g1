Task Analysis and Use Cases

How do we go from "users need to do X" to a precise description of the steps, decisions and system responses that make X possible?

Designing interfaces By Maria Miteva

What is task analysis?

Task analysis is the systematic study of what people do to achieve a goal. Hackos and Redish describe it as a core part of user-centred design: you observe users, identify their goals, and document the tasks they perform in their real environment. The results are often represented as task hierarchies or flow diagrams, depending on what the design team needs to communicate.

Hierarchical Task Analysis (HTA) is one of the most common techniques. It breaks a high-level task into sub-tasks and operations, showing how smaller steps contribute to the overall goal. This helps designers see where an interface can support users efficiently and where it might introduce unnecessary complexity.

Scenarios and use cases

A scenario is a narrative description of a user's interaction with the system: it tells a story about a specific situation, including the user's context, goals and the steps they take. Scenarios are useful for exploring design ideas early, before committing to a detailed specification.

A use case is more formal. IBM's requirements guidance explains that a use case describes a sequence of actions a system performs that yields an observable result of value to a particular actor. Importantly, use cases describe functional requirements but do not specify the user interface itself. They are the foundation for user experience storyboards, which add the screens, navigation and usability requirements needed to design the interface.

User stories vs. use cases

User stories are short, informal statements written from the user's perspective, often in the form "As a [type of user], I want [goal] so that [reason]." They are useful for prioritising work and keeping the focus on user value. Use cases are more detailed and exhaustive: they describe the interactions between the user and the system step by step, including alternative paths and error conditions. Both are valuable, but they serve different purposes in the requirements process.

Example: course enrolment

Consider an information system for university course registration. A task analysis might reveal these steps:

  1. Search for a course by name, code or semester.
  2. Open the course details and check prerequisites.
  3. See how many places are available.
  4. Select a section and confirm enrolment.
  5. Receive a confirmation and see the updated status.

A use case for the same scenario would describe the system's responses at each step, including what happens if a prerequisite is missing or the course is full. This level of detail guides the design of feedback, validation and error recovery in the interface.
