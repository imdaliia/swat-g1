Evaluating Results and Iteration

How can test observations and usability measures guide design improvements?

Information System Engineering Part 3 of 3

Why measure usability?

Usability evaluation combines observations of users attempting tasks with measures that describe the result. Measures help make the evaluation more concrete: they show whether users complete a task, how long it takes, what errors occur and how much help is needed. User-reported ease and satisfaction add the participant's perspective [1].

Possible usability measures

The topic guide identifies five possible measures. Each one describes a different aspect of the user's experience, so it is useful to consider them together with the observations made during the test. Task completion and time are also central measures in usability benchmarking [2].

Measures that can be used in usability evaluation
Measure What it indicates Example question
Task completion rate Whether users are able to complete the task. Did the participant complete the intended task?
Time on task How long users take to complete a task. How long did the task take?
Number of errors How many errors occur while users attempt the task. What errors occurred during the attempt?
Help required How much assistance users need during the task. Did the participant need help to proceed?
User-reported ease and satisfaction How easy or satisfactory users say the experience was. How easy did the participant say the task felt?

Consider measures together with observations

A measure describes part of what happened, while an observation can help explain it. For example, a participant may complete a task but make several errors or require assistance. Looking only at completion would miss those difficulties. Similarly, a task may take a long time because the participant is carefully checking information, so the time should be considered alongside what was observed.

Interpret the whole attempt

Consider task completion, time, errors, help and the participant's reported experience together instead of relying on a single result.

Turn findings into design improvements

The purpose of evaluation is not only to collect results. The team should use what it observed and measured to identify aspects of the interface that may need to change. A useful way to review a finding is to connect the user's difficulty to the part of the task or screen where it occurred, then decide what design change could address it.

From observation to revision

  1. Describe the problem: what difficulty did the participant encounter?
  2. Identify where it happened: which screen or step of the task was involved?
  3. Review the evidence: consider completion, time, errors, help and user-reported ease.
  4. Propose a change: revise the relevant part of the interface.
  5. Test again: check whether the change improves the task attempt.

Example: improving course registration

Imagine that a participant testing a course-registration prototype does not notice the prerequisites before trying to enrol. The observation points to a difficulty in the course-information screen. The team could revise how the prerequisite information is presented and then ask users to attempt the same task again.

During the next test, the team can check whether participants notice the information, whether they complete the task, whether errors or requests for help decrease, and whether they report that the process is easier to understand.

The iterative process

Interface design is iterative. Evaluation findings inform a revision, and further testing checks the effect of that revision. The process can be repeated when problems remain or when a change introduces a new difficulty.

Key message

Test, learn, revise and test again.

Putting the three parts together

  1. Create a prototype using sketches, wireframes or a clickable version.
  2. Test it with representative users performing realistic tasks.
  3. Observe problems and consider the five usability measures.
  4. Revise the design and test again to evaluate the change.
